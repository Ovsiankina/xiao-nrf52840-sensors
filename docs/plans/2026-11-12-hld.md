## API surface (the part to react to)

This is the target, not yet code. Step 4 freezes it.

```rust
use xiao_api::{Accel, Ble, Gyro, Imu, Mic, Uart, Usb};

// 1. Simplest: microphone over USB. The sensor itself is the iterator.
let usb = Usb::open()?;
let mic = Mic::on(&usb)?;                  // powers the mic on the board
for block in &mic {
    let block: AudioBlock = block?;
    let pcm: &[i16] = block.samples();     // block.rate() == Hertz(16_000)
}
// `mic` dropped here: the board powers the mic off.

// 2. Gyroscope over BLE, accelerometer stays off.
let ble = Ble::open()?;                    // default name "XIAO-Sense"
let gyro = Gyro::on(&ble)?;
let r: Rotation = gyro.latest()?;          // r.x, r.y, r.z: Dps(f32)

// 3. Same, configured. Builders only where there is something to set.
let ble = Ble::named("desk-xiao").attempts(5).open()?;
let gyro = Gyro::rate(Rate::Hz104).range(GyroRange::Dps500).on(&ble)?;

// 4. Both halves of the IMU, one link (FW-2).
let imu = Imu::on(&usb)?;
for r in &imu {
    let r: Motion = r?;                    // r.accel: Acceleration (G), r.gyro: Rotation (Dps)
}

// 5. Two sensors, two links at once (FW-1).
let mic = Mic::on(&ble)?;
let accel = Accel::on(&usb)?;
let a: Acceleration = accel.latest()?;     // a.x, a.y, a.z: G(f32)

// 6. UART, with its speed.
let uart = Uart::port("/dev/ttyUSB0").baud(Baud(921_600)).open()?;

// 7. Errors say why.
match Mic::on(&usb) {
    Err(Error::Busy { held_by }) => {}     // held_by: Link::Ble
    Err(Error::TooSlow { needs, link_has }) => {}   // both BytesPerSec
    Err(Error::Timeout { attempts }) => {}
    _ => {}
}

// 8. Dropped readings (API-4).
let lost: Dropped = gyro.dropped();        // count since the stream began
```

Choices in it:

- `on(&link)`, not `on(link)`: one link can carry several sensors.
- Blocking calls, no `async` in the developer's code. The BLE link
  runs its own small runtime inside.
- Each sensor is its own iterator (`for x in &mic`); no `.stream()`
  call. (Owner, 2026-11-12.)
- `Ble::open()` uses the default name `XIAO-Sense`, which the firmware
  advertises; `Ble::named(..)` overrides it. (Owner, 2026-11-12.)
- Outputs are newtypes, never bare numbers: `G`, `Dps`, `Hertz`,
  `Baud`, `BytesPerSec`, `Dropped`; readings are `Acceleration`,
  `Rotation`, `Motion`, `AudioBlock`. (Owner, 2026-11-12.) Audio
  samples stay `&[i16]` inside `AudioBlock`, so audio crates take them
  as they are.
- Dropping a sensor value turns the sensor off (FW-6).
- `Gyro`, `Accel`, `Imu` are top-level types: `Imu::Gyro::on` is not
  valid Rust for a type inside a type.

## Stack

| part | choice | why |
|---|---|---|
| Firmware HAL | `embassy-nrf` 0.11 | one HAL covers I2C, PDM, USB, UART |
| BLE on the board | `trouble-host` 0.8 + `nrf-sdc` 0.4 | on crates.io, same embassy versions; the factory SoftDevice stays in flash, unused |
| USB on the board | `embassy-usb` 0.6, serial class | |
| IMU driver | own register code in `firmware::imu` (about 6 registers, ST's C driver as reference) | no crate is usable without an allocator + `unsafe`, or a fork |
| Mic | `embassy_nrf::pdm`, 1.280 MHz clock | traps listed in the research file |
| Wire format | `postcard` + COBS framing, in `xiao-proto` | small, `no_std`, resyncs after a drop |
| USB and UART off the board | `serialport` 4.10 | both are serial ports |
| BLE off the board | `btleplug` 0.13 (+ `tokio`) | |
| Logging on the board | none; `panic-halt` | no debug probe |

BLE transport: one serial-like service (Nordic UART Service layout): one
characteristic the API writes commands to, one the firmware notifies
messages on.

## Crate layout

```
Cargo.toml            workspace, shared lints
.cargo/config.toml    linker flags for the board target only
scripts/flash.sh      build + flash crates/firmware
crates/proto/         xiao-proto     no_std lib   message, frame
crates/api/           xiao-api       std lib      error, link/{usb,ble,uart}, stream, mic, imu
crates/firmware/      xiao-firmware  lib + bin    sensors, imu | board, mic, link/{usb,ble,uart}, main
```

`cargo test --workspace` runs on the host. In `xiao-firmware`, the
hardware-free modules (`sensors`, `imu`) build and are tested there; the
board-only modules and dependencies are behind `cfg(target_os = "none")`.

## Modules and dependency order

1. `proto` (nothing)
2. `api` → `proto`; `firmware` → `proto` (parallel)

Inside each crate: see the `//!` comment of each file and the C3 views
in `docs/workspace.dsl`.

## Requirement → module

| requirement | module |
|---|---|
| API-1 | `api::link`, `api::mic`, `api::imu` |
| API-2 | `api::link::ble` |
| API-3, API-4 | `api::stream` |
| FW-1, FW-2, FW-4, FW-6 | `firmware::sensors` |
| FW-3 | `firmware::link::uart` |
| FW-5 | `firmware` main loop, `proto::message` |

## Not testable on the host

Anything that needs the board: the links, the mic, real IMU readings,
and the BLE throughput hole. These are checked by hand after flashing.
